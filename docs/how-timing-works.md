# 平台学时计算机制（实测）

> 本文是脚本设计的依据。所有结论来自浏览器 DevTools 抓包，非猜测。
> 如果你打算给这个项目提"能不能加速/跳进度"的建议，请先读完本文。

## 一、抓到的请求

```
[13:50:33] POST /cpvtianjin/study/updateTimeSeconds.do
            body: orderItemId=103830708&seconds=60
            返回: {"error_code":0,"data":"已学习229分钟","success":true}

[13:51:33] POST /cpvtianjin/study/updateTimeSeconds.do   ← 正好 60 秒后
            body: seconds=60
            返回: "已学习230分钟"
```

## 二、三条确定结论

### 1. 上报值恒定，与倍速无关

`seconds=60` **永远是 60**，无论当时播放速度是 1x 还是 4x。

这意味着：服务端每 60 秒给你记 60 秒，**不看你视频走了多远**。

### 2. 学时 = 真实挂机时间

进度 = `已学习分钟数 ÷ 课程总时长`。

实测对照：课程 `4:22:15`（262 分钟），当返回 `已学习 45 分钟` 时，列表页显示 `17%`。
`45 ÷ 262 = 17.2%` ✓

### 3. 服务端会回扣

观察到 `232 分钟 → 229 分钟`，请求体仍是 `seconds=60`。

说明服务端有一层有效性校验，判定某些分钟不算有效学习。可能的影响因素：

- 切倍速
- 跳进度
- 页面切到后台
- 同时在多设备登录

> 因此**伪造 `seconds` 值**不仅无效，还可能触发更严格的校验。

## 三、倍速为什么没用

| 倍速 | 视频播完耗时 | 平台记录 | 需补播 |
|---|---|---|---|
| 1x | 262 分钟 | 262 分钟 | 0 |
| 2x | 131 分钟 | 131 分钟 | 131 分钟 |
| 4x | 65 分钟 | 65 分钟 | 197 分钟 |

**总时长恒为 262 分钟。** 倍速只让视频提前跑完，然后你要么补播、要么学时不够。

这也解释了一个常见现象：**视频 100% 但平台只有 30%**——因为两者不同源。

## 四、三个"百分比"的区别

这是最容易混淆的地方：

| 叫法 | 算法 | 用途 |
|---|---|---|
| **视频位置 %** | `currentTime ÷ duration` | 只反映本次播到哪，**不参与完成判定** |
| **平台累计 %** | `已学习分钟 ÷ 课程总时长` | 服务端口径，但页面不实时显示 |
| **列表页 %** | 服务端另算（含四舍五入） | **脚本以此为准** |

同一时刻三个数可能分别是 `14% / 13% / 18%`，都是对的。

## 五、关于视频播放器

视频源是**腾讯云点播**：

```
POST /common/getVideoToken.do   →  token + sign + ts
埋点上报 → https://v.qidian.qq.com/events/trace
```

播放器内部可能同时存在**多个 `<video>`**（正片 + 片头/广告/预览）。脚本用"时长最长"来识别正片，避免短片段播完被误判为课程完成。

## 六、如果你要验证这些结论

在播放页按 `F12` → Network → 筛选 `updateTimeSeconds`，观察：

1. 请求间隔是不是 60 秒
2. `seconds` 是不是恒为 60
3. 返回的分钟数增长是否与真实时间 1:1（若你开倍速，会发现明显小于 1:1）

或者在 Console 直接看：

```js
// 打开任意一门课，1x 播 5 分钟，记录开始前的"已学习 X 分钟"
// 再切 4x 播 5 分钟，对比增长速度
```
